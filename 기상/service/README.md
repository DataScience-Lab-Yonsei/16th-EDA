# 날씨 기반 여행 점수 서비스 (KTCI)

여행 일정 타임테이블(장소 + 시각)을 입력하면 그 장소·그 날짜의 예보를 API로 불러와
스케일링 사양대로 **0~100점 여행 날씨 점수**를 산출한다.

```
일정  →  시간별 예보  →  일 대표값  →  하위지수 S_* (0~1)  →  계절 가중합 KTCI  →  여행 점수
Stop     providers      aggregate      subindex             scoring            score_itinerary
```

**KTCI는 일 단위 지수다.** 일 대표값(일최고/일최저/일강수합/일최대1시간강수/24시간 평균 PM)
위에서 정의되므로, 점수의 단위도 (장소, 날짜)다. 같은 날 같은 격자의 스탑들은 동일한 KTCI를
공유하고, 스탑 간 차이는 **장소와 노출도·체류시간**에서 나온다.

---

## 1. 하위지수 (`app/subindex.py`)

사양대로 구간선형 보간 + [0,1] 클리핑 + **최댓값 결합**.

| 영역 | 정의 |
|---|---|
| 기온 | `max( heat(AT_주간), cold(AT_야간) )` — UTCI 열/냉 스트레스 구간 |
| 습도 | `max( rh_dev(RH), thi(THI) )` — ASHRAE 40–60% 이탈 + 불쾌지수 |
| 대기질 | `max( PM2.5, PMc, O3, NO2, SO2, CO )` — CAI 등급경계 |
| 바람 | `f(WS_최대)` — 보퍼트 + 강풍특보 (옵션 `wind_blend_mean=True` → 0.7·최대 + 0.3·평균) |
| 강수 | `max( amount(RN_DAY), intensity(RN_HR1_최대) )` |

체감온도는 기상청 공식을 그대로 썼다. 여름은 Stull(2011) 습구온도를 넣은 열지수식,
겨울은 풍속냉각식이며 **적용범위(T≤10℃, V≥4.8km/h) 밖에서는 기온을 그대로** 쓴다.
`PMc = max(PM10 − PM2.5, 0)`으로 조대분획을 분리해 미세분 이중계산을 피한다.

### 앵커표에 없어서 이 코드가 정한 값 (전부 `ASSUMPTION` 주석)

1. **UTCI 극한 등급의 1.00 지점** — 열스트레스 극한은 `>46℃`로 상한이 열려 있어
   직전 구간 폭(8℃)을 연장해 54℃를 1.00으로 뒀다. 이 경우 **폭염주의보 33℃가 0.29,
   경보 35℃가 0.38**이 된다. 관광 맥락에서 특보 수준을 더 무겁게 보고 싶다면
   `Anchors.heat`만 바꾸면 된다 — 여기가 제일 먼저 검토할 지점이다.
2. **THI 앵커** — 4등급(낮음/보통/높음/매우높음, 경계 68·75·80)을 등간격
   0/0.33/0.67에 대응시키고 1.00 지점을 THI 86으로 뒀다.
3. **RH 이탈 앵커** — ASHRAE 40–60%를 0으로, 0%/100%를 1.00으로 하는 선형.

## 2. 일 대표값 (`app/aggregate.py`)

유효조건 **≥18/24 (75%)** 를 변수별로 판정하고, 미달이면 그 항목은 `None`으로 남겨
scoring 단계의 `weighted_available`가 처리하게 한다.

- **강수 결측은 0이 아니다.** 유효시간 미달이면 `rn_day`·`rn_hr1_max` 모두 `None`이다.
  (테스트 `test_precip_missing_is_not_zero`로 고정)
- **O3는 일평균이 아니라 일 최대 8시간 이동평균.** 각 8시간 창은 6시간 이상 유효해야 인정.
- 가스 앵커는 ppm 기준이라 ㎍/㎥로 오는 소스는 `ugm3_to_ppm()`으로 변환한다
  (25℃·1atm, 몰부피 24.45 L/mol).

## 3. 가중치 (`config/ktci_weights.json`)

워크북에서 계산식으로 확정 가능한 부분은 전부 뽑았다. **evidence 공식은 역산에 성공했고
계절가중치 시트 20개 행 전부 오차 2e-6 이내로 재현된다.**

```
evidence    = √( |spearman| × decile_amplitude_log × availability )
data_weight = evidence / Σ evidence                      (계절별 합 = 1)
w_hybrid    = α × w_2014_adapted + (1 − α) × w_data
α = 봄 0.45 / 여름 0.00 / 가을 0.25 / 겨울 0.30
```

| 계절 | thermal | humidity | wind | precipitation | air_quality |
|---|---|---|---|---|---|
| 봄 | 0.279 | 0.128 | 0.127 | **0.347** | 0.118 |
| 여름 | 0.270 | 0.101 | 0.202 | **0.372** | 0.054 |
| 가을 | 0.164 | 0.084 | 0.194 | **0.391** | 0.167 |
| 겨울 | 0.232 | 0.140 | 0.144 | **0.319** | 0.164 |

여름은 α=0이므로 hybrid == data이고, 이는 지수성능 시트의 여름 수치가 두 지수에서
사실상 동일하다는 점과 일치한다 (테스트로 고정).

**결측 규칙** — `weighted_available`: 가용 영역만 남기고 가중치 재정규화, 단 가용 영역이
2개 미만이면 KTCI 결측 (함안군 케이스).

## 4. 지역과 집계

입력 단위는 **날짜별로 방문할 시군구(순서대로)** 다.

```
지역-일 점수 = 그 시군구 좌표의 그날 KTCI
일자 점수    = 그날 방문한 시군구 점수의 평균
여행 점수    = 일자 점수의 평균 (날짜마다 같은 무게)
```

여행 점수를 지역-일 전체 평균이 아니라 **일자 평균**으로 잡았다. 하루에 여러 곳을 도는
날이 있으면 그날 날씨가 과대 반영되기 때문이다. 두 값 모두 응답에 담아
(`trip_score` / `region_day_mean`) 비교할 수 있게 했다.

지역 목록은 워크북 행정계층 시트의 **264곳을 그대로** 쓴다 (`config/regions.json`).
시도와 권역은 signguCode 앞 두 자리에서 유도했다. 이름이 겹치는 곳이 많아서
— **중구 6, 동구 6, 서구 5, 남구·북구 4, 강서구·고성군 2** — 조회 키는 항상
signguCode이고 화면에는 `서울 중구`처럼 시도를 붙여 보여준다.

**좌표**는 `config/regions.json`에 비어 있다. 한 번 채워 두면 이후 지오코딩 호출이 없다.

```bash
python scripts/build_region_coords.py          # Nominatim, 264곳 약 5분
KAKAO_KEY=... python scripts/build_region_coords.py   # 카카오, 훨씬 빠르고 정확
```

안 돌려도 서버가 요청 시점에 지오코딩해 메모리에 캐시하므로 동작은 한다. 다만 첫 요청이
느리고 Nominatim 초당 1회 제한에 걸릴 수 있다.

## 5. 계획 수정 돕기

예보를 어차피 통째로(최대 16일) 받아 두므로, 각 지역마다 **예보 범위 안에서 지금보다
점수가 높은 날짜**를 추가 호출 없이 계산한다. 1점 이내 차이는 권할 이유가 없어 걸러낸다.

응답의 `summary.fixable`은 점수가 낮은 순으로 정렬돼 "강원 강릉시 7/27 51.6점 →
7/26로 옮기면 99.1점" 같은 형태로 나온다. 화면 상단에도 같은 목록이 뜬다.

## 7. 엔드포인트

| | |
|---|---|
| `GET /` | 화면 |
| `GET /regions/search?q=` | 시군구 자동완성 (264곳) |
| `POST /score/trip` | **주 경로.** 날짜별 시군구 목록 → 지역·일자·여행 점수 + 대안 날짜 |
| `POST /score` | 부 경로. 좌표·시간대·노출도 기반 스탑 채점 |

curl -X POST localhost:8000/score/trip -H 'Content-Type: application/json' -d '{
  "days": [

## 8. 화면 (`static/index.html`)

빌드 도구 없는 단일 HTML이고 FastAPI가 `/`에서 서빙한다. 왼쪽에서 날짜를 추가하고
시군구를 검색해 순서대로 담으면, 오른쪽에 여행 전체 점수 → 옮기면 좋은 지역 →
일자별 → 지역별 순으로 나온다.

**시그니처는 기여 막대다.** 5개 영역을 가로로 놓되 **폭 = 계절 가중치**,
**채움 높이 = 스트레스 S**로 그려서 **칠해진 면적이 곧 KTCI**가 되게 했다. 여름에
강수가 막대의 37%를 차지하고 그게 80% 차 있다는 걸 숫자를 읽기 전에 본다.
색은 각 영역이 재는 물질에서 가져왔다 (기온 앰버 / 습도 청록 / 바람 연보라 /
강수 남색 / 대기질 황토). 결측 영역은 빗금으로 비워 둬 스트레스 0과 구분된다.

## 9. VS Code에서 실행

`.vscode/` 설정이 포함돼 있다. 폴더를 열고 인터프리터만 잡으면 **F5**로 서버가 뜬다.

1. **`wtsi` 폴더 자체를 연다.** 상위 폴더를 열면 `app` 모듈을 못 찾는다.
2. 터미널(``Ctrl+` ``)에서 `python -m venv .venv`
3. `Ctrl/Cmd+Shift+P` → `Python: Select Interpreter` → `.venv`
4. `Tasks: Run Task` → `의존성 설치`
5. **F5** → `서버 실행 (자동 새로고침)` → http://localhost:8000

| 실행 구성 | 쓰임 |
|---|---|
| 서버 실행 (자동 새로고침) | 평소 개발용 |
| 서버 디버그 (중단점용) | `--reload` 없음. **중단점을 걸 때는 이쪽** |
| 데모 (오프라인) | 예보 API 없이 채점 로직만 |
| 테스트 전체 | 44개 |

`--reload`는 리로더가 자식 프로세스를 새로 띄워 중단점이 안 붙는 경우가 많다.

설치 없이 코어만 확인하려면 `python demo_offline.py`, `python run_tests.py`
— 둘 다 외부 패키지 0개로 동작한다. `api.http`는 REST Client 확장용 스크래치 파일이다.

## 10. 남은 작업

1. **CSV로 앵커 검증** — `airkorea/asos/aws_2023_2025_normalized.csv`가 이미 정규화된
   S_* 값이면 이 코드의 하위지수와 직접 대조할 수 있고, 원 변수 CSV면 `DailyObs`에 넣어
   워크북 KTCI를 재현해 보면 된다. **가장 가치 있는 다음 단계다** — 3개 `ASSUMPTION`이
   여기서 정리된다.
2. **회귀 테스트** — 3년치로 산출한 KTCI가 지수성능 시트의 spearman(전국 hybrid 0.166,
   제주권 0.274)을 재현하는지.
3. **좌표 정밀화** — 지금은 시군구 대표점 1개다. 면적이 넓은 군(홍천군 등)은 대표점과
   실제 방문지의 날씨가 다를 수 있다. 관광지 좌표를 따로 받는 편이 정확하다.
4. **권역 보정** — `region_group`을 이미 들고 있으니, 지수성능 시트의 권역별 성능차를
   반영해 권역별 가중치를 쓰는 선택지를 열 수 있다.
5. **예보 범위 밖** — 대기질 5일, 기상 16일 너머는 평년값 기반 기후 점수로 폴백.
